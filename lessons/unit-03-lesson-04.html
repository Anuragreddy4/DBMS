UNIT 03 · LESSON 04

Lossless & dependency-preserving decomposition

IN PLAIN WORDS

Decomposition splits one relation into smaller relations. A good split lets us join the pieces back without inventing rows and keeps important rules checkable.

By the end, you can:
  • Tell lossless join from dependency preservation
  • Apply the binary lossless test
  • Explain the purpose of the chase/tableau
TOPICS IN THIS LESSON
01Lossless-join decomposition↘02Dependency preservation↘03Chase / tableau test↘04Problems caused by a poor decomposition↘
EXPLANATION
TOPIC 01

Lossless-join decomposition

DEFINITION

A decomposition is lossless if joining its pieces recreates exactly the valid rows of the original relation.

A lossy split can create spurious tuples—combinations that never existed—or lose the original connections.

For a binary split R1 and R2, a standard sufficient test is that the common attributes functionally determine all of R1 or all of R2.

QUICK EXAMPLE

If R(A,B,C) is split into AB and AC, the common attribute A must determine B or determine C for this standard binary test.

TOPIC 02

Dependency preservation

DEFINITION

A decomposition is dependency-preserving if the rules projected onto the smaller relations still imply all the original dependencies.

When dependencies are preserved, each rule can be checked on a local table without joining several tables.

Losslessness and dependency preservation answer different questions; check both.

QUICK EXAMPLE

If A→B remains entirely inside R1(A,B), the DBMS can enforce it there.

TOPIC 03

Chase / tableau test

DEFINITION

The chase is a table-based procedure that applies dependencies to rows of symbols to test whether a decomposition is lossless.

Give each decomposed relation a row with distinguished symbols for included attributes and unique symbols for missing attributes.

Apply dependencies to make agreeing determinant columns agree on dependent columns. If a row becomes all distinguished symbols, the decomposition is lossless.

QUICK EXAMPLE

The chase is useful when there are more than two decomposed relations and the simple binary test is not enough.

TOPIC 04

Problems caused by a poor decomposition

DEFINITION

A decomposition can be harmful if joining the pieces invents rows or if important dependencies can no longer be checked locally.

A lossy decomposition produces spurious tuples: the join contains combinations that were not valid in the original relation.

A decomposition that is not dependency-preserving may require joins to enforce an original rule. This increases work and can let invalid states pass if checks are not coordinated.

Test both properties separately: losslessness protects reconstruction meaning; dependency preservation protects local rule checking.

QUICK EXAMPLE

Suppose a relation records which student studies which subject with which instructor. A split that keeps only student-subject and student-instructor can recombine an instructor with a subject the student never took. The extra joined row is spurious.

WORKED EXAMPLE · SELECT A STEP

Split a table and join it back without inventing rows

Asha takes DBMS and OS. Bilal takes DBMS. We split student names from course registrations.

Original rows
1, Asha, DBMS
1, Asha, OS
2, Bilal, DBMS
STEP 01

Find what belongs to Student

Student ID 1 always means Asha, and ID 2 means Bilal. Put each ID and name in STUDENT once.

STEP 02

Find what belongs to Enrollment

Put each Student ID and Course pair in ENROLLMENT. The ID connects it to the student.

STEP 03

Join the two tables

Match equal Student IDs. The result is the same three original rows; no extra student-course pair appears.

RESULT

This split is lossless because joining the two smaller tables rebuilds exactly the original rows. The student-name rule stays together in STUDENT.

EXAM FOCUS

What to be ready to explain

Define lossless and dependency-preserving decomposition, apply the binary test, and explain what the chase/tableau establishes.
