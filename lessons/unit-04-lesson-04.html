UNIT 04 · LESSON 04

Recoverable, cascadeless & strict schedules

IN PLAIN WORDS

Recoverability is about commit order after a read. Cascadeless and strict schedules add stronger rules that make failures easier to handle.

By the end, you can:
  • Recognize a dirty read
  • Classify recoverable, cascadeless, and strict schedules
  • Explain the implication between the three
TOPICS IN THIS LESSON

EXPLANATION
TOPIC 01

Recoverable schedule

DEFINITION

If T2 reads a value written by T1, a recoverable schedule makes T2 commit only after T1 commits.

If T1 aborts, T2 must still be allowed to roll back before its own commit.

Recoverability protects committed results from depending on work that may be undone.

QUICK EXAMPLE

T1 writes A; T2 reads A; T1 commits; then T2 commits. This order is recoverable.

TOPIC 02

Cascadeless schedule

DEFINITION

A cascadeless schedule allows a transaction to read a value only after the transaction that wrote it has committed.

This prevents dirty reads and avoids a chain of dependent transactions all needing to abort.

It is stricter than recoverability because it delays the read itself, not just the reader's commit.

QUICK EXAMPLE

If T1 has written A but not committed, T2 waits before reading A.

TOPIC 03

Strict schedule

DEFINITION

A strict schedule prevents other transactions from reading or writing an item that a transaction has written but not yet committed or aborted.

The waiting rule protects both reads and overwrites of uncommitted values.

Strictness makes undo simpler because an uncommitted value has not escaped to another transaction.

QUICK EXAMPLE

After T1 writes A, both T2's read(A) and write(A) wait until T1 finishes.

WORKED EXAMPLE · SELECT A STEP

Spot a decision based on an unconfirmed payment

T1 records that Asha paid her fee, but has not finished. T2 sees “Paid” and issues Asha a hall ticket. Then T1 fails and the payment is cancelled.

StepWhat the database shows
T1 changes payment statusPaid, but not confirmed
T2 reads the status and commitsHall ticket issued
T1 abortsPayment status returns to Unpaid
STEP 01

Notice the unconfirmed change

T1 marked the fee as paid, but it has not committed. The DBMS may still cancel this change.

STEP 02

T2 acts on that change

T2 reads “Paid” and commits the hall-ticket decision before T1 has finished.

STEP 03

T1 is cancelled

The payment is undone, but the hall-ticket decision has already been committed using that temporary value.

RESULT

T2 read data that was not yet confirmed. This is a dirty read, and the schedule is not recoverable because T2 committed before the transaction it depended on.

EXAM FOCUS

What to be ready to explain

Given a schedule, determine whether it is recoverable, cascadeless, or strict. Explain dirty reads and cascading rollback.
